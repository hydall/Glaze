# Рендеринг сообщений: почему карточки ломаются и как это чинить основательно

**Статус:** аудит + план. Ничего из этапов 0–3 ещё не сделано.
**Область:** `assets/chat_webview/formatter/`, `assets/chat_webview/renderer/`,
тесты WebView-ассетов.
**Повод:** шесть точечных фиксов подряд в одном и том же месте за десять дней.

| Дата | Коммит | Что чинили |
|---|---|---|
| 19.08 | `171913d` (#290) | `<style>` и inline-стили вырезались при выключенном JS |
| 26.08 | `7d9cd78` (#321) | display-регекс затирал исходный текст сообщения |
| 27.08 | `3970224` (#325) | тумблер скриптов менял политику вставки всей разметки |
| 27.08 | `bd0606a` (#326) | форматтер ломал карточки: `<br>`, `<source>`, таблицы, списки, заголовки |
| 28.08 | `254a1cc` (#339) | `:target`-карточки и ссылки внутри сообщения не кликались |
| 28.08 | `f7477cf` | `<script>` карточки не объявлял функцию для своего `onclick` |

Каждый фикс был правильным и каждый закрывал ровно один заявленный случай.
Это и есть проблема: мы чиним по жалобам, а не по причинам. Ниже — три
причины и план, который их снимает.

---

## Причина 1. Форматтер угадывает структуру вместо того, чтобы её разбирать

`Formatter._processText()` (`formatter/formatter.js`) — 25 нумерованных шагов
и ~450 строк, которые обрабатывают **строку**, где перемешаны markdown, HTML и
проза. Структура не разбирается, а угадывается тремя эвристиками:

* **«Сирота»** (`formatter.js:427`): тег экранируется в видимый текст, если имя
  этого тега встречается во всём сообщении ровно один раз.
* **Хардкод блочных тегов** (`formatter.js:414`): `blockTags` — список из 40
  имён, в котором уже сидит `loomledger`, добавленный под конкретную карточку.
  Всё, чего нет в списке, считается инлайновым.
* **Ручная расстановка абзацев** (шаг 11): текст режется по `\n\n`, каждый
  кусок оборачивается в `<p>`, а исключения (плейсхолдер-блоки, абзац из одних
  тегов) перечислены отдельными правилами.

Каждая карточка, которая чуть отличается от предыдущей, попадает в необслуженную
ветку одной из трёх эвристик. Прогон текущего `main` (Chromium, реальный
`Formatter.format`) — все три бьют прямо сейчас:

```
вход:  <table><tr><th>Стат</th></tr></table>
выход: <table><p><tr><th>Стат</th></tr></p></table>
       → tr/th/td нет в blockTags, поэтому внутрь таблицы вставлен <p>;
         браузер выбрасывает его наружу, ломая селекторы вида table > tr

вход:  <input type="checkbox" id="t1"><label for="t1">жать</label><div class="ov">скрыто</div>
выход: <p><input type="checkbox" id="t1"><label for="t1">жать</label></p><div class="ov">…</div>
       → CSS-only карточка ST: #t1:checked ~ .ov больше не матчится,
         потому что input и .ov перестали быть соседями.
         #326 чинил ровно это, но только для абзаца БЕЗ текста —
         текст «жать» внутри <label> выводит случай из-под правила

вход:  <div class="card"><b>Sandrone</b>\nещё печатает      (незакрытый — стриминг)
выход: <p>&lt;div class="card"&gt;<b>Sandrone</b> ещё печатает</p>
       → пока не пришёл </div>, карточка показывается как голый текст
         с тегами; это то самое «мигание» во время генерации
```

Ни один из этих трёх случаев не был заявлен как баг. Их просто ещё не заметили.

## Причина 2. Мы рендерим в shadow root, а карточки написаны под документ

Тело сообщения пишется в `.message-content` → `attachShadow({mode:'open'})`
(`renderer/message_renderer.js:643`). Изоляция стилей за это платит тем, что
любая карточка, рассчитывающая на семантику документа, ломается — и мы
открываем эти дыры по одной, по мере жалоб:

| Возможность документа | Состояние |
|---|---|
| `#fragment` + `:target` | зашимлено в #339 (`renderer/target_toggle.js`) |
| ссылки внутри сообщения | зашимлено в #339 (`composedPath` в диспетчере) |
| глобальная область `<script>` | зашимлено сегодня (`f7477cf`) |
| `document.getElementById` / `querySelector` | зашимлено сегодня (`renderer/shadow_document_shim.js`) |
| `@import` в `<style>` | **не работает**, браузер игнорирует его в shadow root (нашли сегодня: шрифт карточки молча падает в `cursive`) |
| `document.body.appendChild` (модалка/оверлей карточки) | **не работает как ожидается**: узел уходит из-под CSS сообщения и рендерится без стилей |
| `DOMContentLoaded` / `window.onload` | **никогда не сработает** — документ давно загружен, карточка ждёт события впустую |
| `getElementsByClassName` / `getElementsByTagName` / `document.forms` | **не зашимлено** |
| `document.styleSheets`, `element.animate` по селектору из документа | **не зашимлено** |

Список дыр конечен, но нигде не записан. Пока он не записан целиком, каждая
следующая карточка — это новая жалоба и новый патч.

## Причина 3. Тесты не рендерят

`test/webview_assets_test.dart` — 2400 строк **строковых** проверок вида
`expect(js, contains('...'))`. Они пиннят форму кода: что вызов есть, что он
стоит раньше другого. Ни один тест не строит DOM, не применяет CSS и не жмёт
кнопку. Поэтому:

* регрессию находит пользователь, а не CI;
* починенный случай защищён ровно настолько, насколько дословно совпадает
  строка в тесте — переименование переменной снимает защиту;
* чтобы проверить сегодняшний фикс, пришлось вручную поднимать Chromium.

## Как это устроено в SillyTavern (сверено по исходникам `release`)

`public/script.js:1753 messageFormatting()`:

1. макросы → regex-скрипты (`getRegexedString`, `isMarkdown: true`);
2. опционально `fixMarkdown`, опционально экранирование всех тегов;
3. кавычки → `<q>` одним регексом, который заранее защищает `<style>`,
   ``` ``` ```-блоки и инлайн-код;
4. **`converter.makeHtml(mes)` — showdown** (`script.js:521`, опции: `tables`,
   `simpleLineBreaks`, `literalMidWordUnderscores`, `parseImgDimensions`,
   `underline`, `strikethrough`, `disableForced4SpacesIndentedSublists`);
5. `DOMPurify.sanitize` с `MESSAGE_SANITIZE`;
6. вставка в **light DOM** (`.mes_text`).

`<style>` при этом ST переписывает: вынимает в `<custom-style>`, парсит CSS и
возвращает с префиксом `.mes_text ` для каждого селектора, а все классы в
разметке и в CSS переименовывает в `.custom-*` (`scripts/chats.js:536-600`,
hook на `uponSanitizeAttribute`, `chats.js:1910`). То есть ST работает с
разметкой сообщения **менее** дословно, чем мы, — изоляцию он покупает
переписыванием селекторов, а не shadow root.

**Важное следствие.** DOMPurify в конфигурации ST не разрешает `<script>` и
вырезает все `on*`-атрибуты. Значит в ванильной таверне JS-карточек не бывает
вообще: то, что «работает в таверне», работает на CSS — `:target`, скрытый
чекбокс + `~`, `<details>`. JS-карточки приходят из Risu и из расширения
TavernHelper, где карточка исполняется в отдельном **iframe** с настоящим
документом — там ни один шим не нужен по построению.

Отсюда приоритет: главный разрыв совместимости у нас — **разметка и CSS**
(причина 1), а не JS. JS мы поддерживаем шире, чем ST, и платим за это
шимами (причина 2).

## План

### Этап 0. Корпус карточек + браузерный харнесс (≈1 день) — делать первым

`test/webview_js/` — прогон настоящих модулей (`formatter/index.js`,
`renderer/markdown.js`) в headless Chromium через Playwright:

* корпус — реальные карточки: дневник кинков, карточки из #326, #339, #325,
  CSS-only чекбокс, HTML-таблица, `<details>`, SVG-иконка, стрим-префиксы
  (первые N символов каждой карточки — проверка, что на полпути ничего не
  «мигает»);
* ассерты — на итоговый DOM (`shadowRoot.innerHTML`), на применённый CSS
  (`getComputedStyle`), на клик (кнопка раскрывает панель) и на то, что в
  видимом тексте нет `<`, `>` от съеденных тегов;
* отдельная job в CI: Node + Playwright, без Flutter, ~1 минута.

Правило после этого этапа: **каждый баг рендера сначала становится записью в
корпусе, и только потом чинится.** Это то, что превращает бесконечные латки в
конечный список.

### Этап 1. Настоящий разбор вместо угадывания (≈2–3 дня)

Двухфазный рендер вместо строкового конвейера:

* **Фаза A — разбор.** Текст сообщения разбирается браузерным парсером
  (`<template>.innerHTML` / `DOMParser`): HTML становится деревом, проза —
  текстовыми узлами. Никакого счётчика «сирот», никакого списка блочных тегов,
  никакой ручной расстановки `<p>` внутри чужой разметки. Незакрытый тег
  браузер закрывает сам — стриминг перестаёт мигать.
* **Фаза B — markdown только по текстовым узлам.** Кавычки, `==маркеры==`,
  `**жирный**`, списки, таблицы, заголовки применяются к тексту, а не к
  строке, содержащей теги. Атрибуты и содержимое `pre/code/script/style`
  недостижимы по построению.
* Для самого markdown разумно взять **showdown с опциями ST** (пункт 4 выше):
  это даёт паритет с таверной по построению, а не по списку починенных
  случаев. Наши расширения (`==hc:==`, imagegen-блоки, `{{макросы}}`,
  janitor-картинки) остаются отдельными пассами до/после.

Снимает разом: `<p>` внутри таблиц и карточек, разъезд соседних элементов
(CSS-only чекбокс), экранирование одиночных тегов, поедание markdown внутри
атрибутов, мигание при стриминге, хардкод-списки.

Риск: изменится вывод в краевых случаях. Именно поэтому этап 0 идёт первым —
корпус фиксирует, что считается правильным, до рефакторинга.

### Этап 2. Явный контракт документа (≈1–2 дня)

Один модуль `renderer/message_document.js` вместо россыпи шимов, и один раздел
в `INVARIANTS.md`, где перечислено **всё**, на что карточка вправе
рассчитывать внутри shadow root: id и фрагменты, `:target`, глобальные
скрипты, `document.*`-запросы, `@import` (поднимать в head документа),
`document.body.appendChild` (переадресовывать в оверлей-слой сообщения),
синтетические `DOMContentLoaded`/`load` после вставки, `getElementsBy*`.
Каждый пункт — запись в корпусе из этапа 0. Дыры закрываются списком, а не по
жалобам.

### Этап 3 (опционально). iframe для карточек с `<script>`

Если после этапа 2 JS-карточки всё ещё будут доставлять баги: рендерить
**только** те карточки, которые несут собственный `<script>`, в
sandbox-iframe — механика уже есть в `bridge/panel_host.js` (srcdoc,
`allow-scripts`, `ResizeObserver` → высота). Внутри iframe документ настоящий,
шимы не нужны вовсе, и это ровно та модель, в которой такие карточки писались
(TavernHelper, Risu). Проза и обычные CSS-карточки остаются в shadow root —
быстро и под нашими стилями.

## Чего делать не надо

* **Не выкидывать shadow root ради light DOM «как в ST».** Мы получим ровно
  тот набор проблем, который ST решает переименованием классов в `.custom-*` и
  префиксом `.mes_text ` у каждого селектора: CSS сообщения начнёт течь в
  чат-хром, а карточки — ломаться от переименования. Изоляция у нас лучше;
  платить за неё надо контрактом (этап 2), а не отказом от изоляции.
* **Не добавлять новые правила в шаг 6 форматтера.** Любое новое исключение в
  эвристике «сироты»/`blockTags` — это следующая жалоба через неделю.
* **Не чинить карточку, не добавив её в корпус.** Иначе следующий рефакторинг
  снова её сломает.
