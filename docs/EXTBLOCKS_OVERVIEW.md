# ExtBlocks: всё, что происходит вокруг основного ответа

Основная модель в Glaze отвечает за текст сцены. Но иногда одной прозы недостаточно: после ответа нужно обновить статус персонажа, создать иллюстрацию, выполнить автоматизацию или показать интерактивную панель.

Для этих задач существует `ExtBlocks` — система дополнительных блоков, работающих вокруг обычной генерации.

Удобная метафора: **основная модель — актёр на сцене, а ExtBlocks — закулисная команда**. Пока актёр произносит реплику, команда может подготовить справку, нарисовать декорацию, запустить механизм или развернуть панель управления.

ExtBlocks не являются частью Studio preset. У них свои пресеты, настройки, API-профили, разрешения и результаты.

## Что умеют ExtBlocks

Типов блока четыре, и они отличаются тем, **как блок получает содержимое**, а не тем, что с этим содержимым потом делают:

| Тип | Что делает |
|---|---|
| **Generated** | Берёт содержимое у модели или из поля блока. |
| **Script** | Выполняет JavaScript в изолированной среде. |
| **Rewrite** | Переписывает само сообщение — целиком или правками search/replace. |
| **Accumulation** | Хранит YAML-документ состояния, который обновляет блок-обновитель. |

Набор совпадает с оригинальным расширением один в один, поэтому пресет переживает круговой импорт-экспорт без приближений.

Раньше типов было шесть: `infoblock`, `imageGen`, `jsRunner`, `interactive`, `rewrite` и `accumulation`. Первые четыре шли к модели **одним и тем же вызовом** и расходились только в том, что делали с ответом — карточка, картинка, JS, iframe. Это различие теперь выражено полями, а не типом:

- картинка рисуется, если в содержимом есть тег `[IMG:GEN]` — ровно как в сообщении чата;
- `render` выбирает, куда попадёт готовое содержимое: карточка в панели или sandboxed iframe;
- `source` выбирает, откуда берётся содержимое: у модели (`prompt`) или с самого блока (`staticContent`, а у script-блока — `script`).

Из-за этого стали возможны сочетания, которых при раздельных типах не существовало: инфоблок, который сам рисует иллюстрацию; панель, написанная руками без обращения к модели; карточка с несколькими картинками.

Результаты обычно отображаются отдельно от основной прозы. По умолчанию они не возвращаются в промпт будущих ответов.

## Пресет ExtBlocks

`ExtensionPreset` — это набор блоков, которые должны работать вместе. В нём хранятся:

- название;
- порядок блоков;
- параметры каждого блока;
- профили LLM API;
- разрешения для JavaScript.

Одновременно активен не более одного пресета. По умолчанию ExtBlocks выключены и активный пресет не выбран.

Выбор пресета в настройках автоматически включает расширение. Выбор пункта **«Не выбран»** убирает активный пресет, но сам общий переключатель может остаться включённым.

### Блоки персонажа

Как в оригинале, блоки могут лежать в самой карточке персонажа: в
`data.extensions.ExtBlocks`, массивом в формате оригинала. Карточки из
SillyTavern приходят с ними сами — расширения карточки при импорте сохраняются
целиком — и уносят их с собой при экспорте.

- Блоки карточки работают в чатах этого персонажа вместе с блоками активного
  пресета, как `BlockService.getAllBlocks` в оригинале: сначала блоки карточки,
  затем блоки пресета; блок карточки заменяет блок пресета с тем же именем.
- Они работают на подключении, профилях и разрешениях активного пресета. Без
  активного пресета ExtBlocks выключены, блоки карточки тоже.
- Список виден в панели ExtBlocks, открытой из чата, группой «Блоки
  персонажа»: добавить, импортировать, изменить, выключить, дублировать,
  экспортировать, удалить. Изменения пишутся в карточку.
- Рядом с полями оригинала у каждого блока лежит ключ `glaze` — полная копия
  блока в формате Glaze с настройками, которых в оригинале нет (вид вывода,
  политика контекста и т.п.). Копия используется, только пока поля оригинала
  ей соответствуют: если блок правили в SillyTavern, побеждает его версия.
- Блокам без `id` выдаётся постоянный id из позиции и имени, чтобы их
  результаты не терялись между чтениями.
- Код: `services/card_blocks.dart` (`cardBlocksOf`, `withCardBlocks`,
  `effectiveExtBlocksPreset`, `saveCardBlocks`).

## Общие настройки блока

Каждый блок определяет:

- тип и название;
- включён ли он;
- момент запуска;
- позицию в цепочке;
- нужно ли ждать предыдущий блок;
- сколько сообщений истории передать;
- сколько старых результатов того же блока добавить;
- какой API использовать;
- показывать ли результат только в панели или также добавить его в будущий промпт;
- разрешён ли автоматический запуск.

По умолчанию новый блок:

- включён;
- запускается после ответа ассистента;
- видит 10 последних сообщений до точки запуска;
- не зависит от предыдущего блока;
- не инжектируется в основной промпт;
- может запускаться автоматически.

## Generated

**Generated** — основной тип. Он проходит три шага, и каждый пропускается, если блоку нечего на нём делать.

```text
prompt → модель ──┐
                  ├─→ содержимое ─→ [IMG:GEN]? ─→ картинки ─→ render
staticContent ────┘
```

### 1. Содержимое

При `source: model` Glaze собирает историю вокруг anchor-сообщения, при необходимости добавляет прошлые результаты этого же блока и передаёт модели инструкцию и шаблон.

При `source: carried` содержимое берётся из `staticContent` как есть, без обращения к модели.

Источник хранится отдельным полем, а не выводится из пустоты `prompt`. Из-за вывода по пустоте редактор был вынужден затирать поля другой стороны, чтобы выбор «прилип»: переключение на «задано здесь» теряло промпт, шаблон и подключение, а обратно — разметку. Теперь блок может держать обе стороны одновременно, и переключение обратимо.

Разбор ответа определяет **только `template`**:

- шаблон непустой → из ответа извлекается содержимое его тегов; если тегов нет, непустой ответ сохраняется целиком;
- шаблон пустой → сохраняется весь ответ, и промпт блока уходит в system-сообщение без добавленного правила формата.

Ответ, целиком завёрнутый в один markdown-фенс, разворачивается — так же, как это делает оригинальное расширение.

Типичные применения: состояние персонажей, краткое содержание сцены, список предметов, показатели отношений, справка о локации.

### 2. Картинки

Если в содержимом есть `[IMG:GEN]` или `data-iig-instruction`, оно проходит через `ImageGenService.processMessageImages` — **тот же вызов, которым рисуются картинки в сообщении чата**. Отсюда блок получает то, чего у отдельного image-типа не было:

- рисуются все теги содержимого, а не только первый;
- упавшая картинка превращается в error-карточку с возможностью повтора, а весь блок остаётся готовым;
- параллельная генерация, когда она включена в настройках;
- референсные изображения и настройка «использовать эндпоинт чата» (блок подставляет своё подключение, раньше туда уходила пустая строка).

Готовые PNG сохраняются в каталог `generated`, а в содержимом остаётся ссылка на локальный путь. При включённом image context новый запрос может получить до трёх последних готовых изображений ExtBlocks в качестве референсов.

Если глобальная генерация изображений выключена, теги приводятся к «отключённому» виду, а текстовое содержимое всё равно сохраняется.

Отдельная команда **«Картинка»** повторяет только отрисовку: сохранённые результаты возвращаются в состояние `pending` и рисуются заново, без нового обращения к модели. Кнопка показывается по содержимому блока, а не по его типу, поэтому доступна любому блоку, у которого картинка есть.

### 3. Куда попадает результат

Поле `render`:

- `card` — санитизированный HTML или текст в панели ExtBlocks под сообщением;
- `panel` — интерактивная панель в отдельном sandboxed `iframe`;
- `message` — внутри самого сообщения, как в оригинальном расширении.

В режиме `message` готовый блок дописывается в конец показанного ответа — в своём теге и без рамки, через перевод строки, ровно как `display_text` оригинала. Затем текст целиком проходит через макросы, регексы отображения и markdown. Поэтому регекс, который в SillyTavern оформлял тег блока, оформит его и здесь. Сохранённый текст сообщения не меняется: блок не попадает ни в редактор, ни в промпт (для этого есть инжект). Пока блок генерируется, ждёт или упал, его строка остаётся в панели — там видны статус, ошибка и кнопка перезапуска. С `hide_display` блок не показывается нигде. Generated- и accumulation-блоки, импортированные из оригинала, получают `message` по умолчанию. Script-блоки в сообщении не показываются никогда — в оригинале скрипт ничего не выводит сам.

Панель может сообщить Glaze о готовности, изменить свою высоту, закрыться или отправить действие через разрешённый мост. Начальная высота хранится в `panelMinHeight`. HTML панели проходит через расширитель макросов перед передачей в iframe.

Это позволяет делать карточки состояния, кнопки выбора, мини-интерфейсы и небольшие интерактивные виджеты — при этом блок остаётся обычным generated-блоком и умеет всё остальное: шаблон, инжект, историю, картинки.

## Script

`Script` выполняет JavaScript в изолированной среде. Он поддерживает два сценария.

### JavaScript от LLM

Модель получает задачу и возвращает код. Glaze извлекает JavaScript, запускает его и сохраняет возвращённое значение как содержимое блока.

Если в ответе модели не найден код, блок завершается ошибкой.

### Готовый скрипт

При `source: carried` готовый JavaScript из `script` выполняется напрямую без обращения к модели. Редактор блока позволяет править это поле — раньше готовый скрипт можно было только импортировать.

Скрипт получает контекст с:

- сообщениями;
- идентификаторами сессии и персонажа;
- именем и описанием персонажа;
- его характером и сценарием;
- результатом предыдущего блока, если он был передан по цепочке.

Через API `window.glaze` скрипт также может работать с разрешёнными переменными, запускать генерацию, временно добавлять данные в промпт, воспроизводить звук, выполнять команды и показывать уведомления.

## Rewrite

`Rewrite` не оставляет результата в панели: модель переписывает само сообщение, и оно сохраняется с новым текстом. Блок работает как в оригинальном расширении.

- Переписываемый текст подставляется в макрос `{{textToRewrite}}`.
- `rewrite_mode: full` — модель возвращает новый текст внутри `<rewritten text>…</rewritten text>`. Если таких тегов несколько, их содержимое склеивается.
- `rewrite_mode: search_replace` — модель возвращает правки в формате `<<<<<<< SEARCH / ======= / >>>>>>> REPLACE`. Каждый SEARCH должен встречаться в тексте ровно один раз, иначе правка отклоняется целиком. Ответ `NO_CHANGES` значит, что менять нечего, и это успешный результат. Шаблон блока в этом режиме заменяется инструкцией формата, а сам протокол уходит отдельным системным сообщением.
- С включённым `apply_regex` к новому тексту (в режиме search/replace — к каждому REPLACE) применяются регексы промпта.
- Несколько rewrite-блоков на одном сообщении выполняются по очереди, и каждый следующий переписывает результат предыдущего. Сообщение сохраняется один раз, в конце.

### Порядок в цепочке

Цепочка сообщения идёт в порядке оригинала:

1. Accumulation — по обновителям в тексте сообщения.
2. Готовые скрипты (`source: carried`, без «Ждать предыдущий»), у которых `execution_order: before`.
3. Rewrite-блоки с `generation_order: before`.
4. Generated-блоки и остальные скрипты — обычной цепочкой.
5. Rewrite-блоки с `generation_order: after`.
6. Готовые скрипты с `execution_order: after`.
7. Accumulation — по обновителям в выводе generated-блоков.

Rewrite на `After User` переписывает сообщение пользователя до того, как модель начнёт отвечать, и ответ строится уже по новому тексту.

### Вручную

В меню сообщения есть пункт **«Переписать…»**, если в активном пресете есть включённые rewrite-блоки. В нём выбирается блок, а также можно указать:

- **фрагмент** — текст, который встречается в сообщении ровно один раз; переписан будет только он. Если оставить поле пустым, переписывается всё сообщение;
- **дополнительную инструкцию**, которая подставляется в `{{additionalPrompt}}`.

Это замена всплывающему окну выделения из оригинала.

## Accumulation

`Accumulation` хранит состояние — YAML-документ, например инвентарь, деньги или отношения, — и не обращается к модели. Состояние меняет **блок-обновитель**: тег `<updater_name>` в тексте сообщения или в выводе generated-блока. Внутри тега — операторы в стиле MongoDB в формате YAML:

```yaml
<stats_update>
$inc:
  gold: 10
$push:
  inventory: Sword
$set:
  status.is_happy: true
  "knownLocations.$[elem].visited": true
arrayFilters:
  - "elem.name": "Village"
</stats_update>
```

- Поддерживаются `$set`, `$unset`, `$inc`, `$mul`, `$min`, `$max`, `$rename`, `$push` (с `$each`, `$position`, `$sort`, `$slice`), `$addToSet`, `$pop`, `$pull`, `$pullAll`, `$currentDate` и `$bit`. Пути пишутся через точку, числовая часть — индекс в списке, `$[]` — все элементы, `$[имя]` — элементы, подходящие под `arrayFilters`. `condition` на верхнем уровне — запрос, которому документ должен соответствовать, иначе обновление не применяется.
- Ключи без `$` попадают в `$set`, а список в `$push` / `$addToSet` добавляет каждый свой элемент — как в оригинале.
- Блок срабатывает только на той стороне, что включена в триггерах (`After User` / `After Assistant`), и только если в тексте есть его обновитель. Ключевое слово и период к нему не применяются.
- Обновление идёт в два прохода, как в оригинале: сначала по тексту сообщения — до остальных блоков, — затем по выводу generated-блоков под этим сообщением.
- Новое состояние сохраняется под сообщением, в котором пришло обновление, а следующее обновление берёт последнее состояние до него. Поэтому у каждого свайпа своя история. Повторный запуск блоков пересобирает состояние сообщения с нуля и не применяет `$inc` дважды. Кнопка перезапуска у самого accumulation-блока делает то же самое.
- Состояние, которое не разбирается как YAML, читается как пустое, и показывается уведомление. Обновление, которое нельзя применить (например, `$inc` к строке), отбрасывается целиком.
- Где показывать состояние, выбирает «Показать как»: в панели (как есть, текстом) или **в тексте сообщения** — как в оригинале, в конец сообщения, обновившего состояние, в виде `<имя блока>…yaml…</имя блока>`, через регексы отображения и markdown. Блоки из оригинала импортируются с показом в сообщении. `hide_display` убирает состояние отовсюду. С включённой инъекцией последнее состояние попадает в промпт по role / position / depth блока, обёрнутое в `<имя блока>`.
- В редакторе блока есть пункт **«Скопировать инструкцию для обновителя»** — тот же текст для модели, что копирует оригинал.

## Когда запускаются блоки

У блока, как в оригинальном расширении, два независимых переключателя: **после сообщения пользователя** и **после ответа**. Включены оба — блок работает в обеих цепочках. Ни одного — блок сам не запускается. Старые блоки, у которых есть только `trigger: afterUser`, читаются как «только после пользователя».

Поверх стороны действует условие сообщения (`blockConditionsMet`):

- **Ключевое слово** (`keyword`). Если задано, блок запускается, только когда оно есть в сообщении-триггере. С `keyword_is_regex` это регулярка; `/шаблон/флаги` читается как JS-литерал (`i`, `m`, `s`, `u`; `g`/`y` отбрасываются, неизвестный флаг отключает все флаги). Невалидная регулярка не срабатывает никогда.
- **Период** (`period`), если ключевого слова нет. Счёт идёт по индексу сообщения во всём чате (приветствие — 0): ответ запускает блок при `index % period == 0`, сообщение пользователя — при `(index - 1) % period == 0`. Период 2 в обычном чате — это каждый ход, 4 — каждый второй.

Условия применяются к автоматическим запускам. Ручной Run All запускает все блоки цепочки `After Assistant` без проверки ключевого слова и периода.

### После свайпа и при старте генерации

Script-блоки с флагом **«После свайпа»** запускаются при каждом свайпе ответа — на существующий вариант или на новый. Блоки с флагом **«При старте генерации»** запускаются до сборки запроса основного ответа, и генерация их ждёт, поэтому то, что скрипт внедрит в промпт, попадает в этот же ответ.

Оба режима — только для side effects, как и в оригинале: `InfoBlock` не создаётся. Выполняется лишь готовый JavaScript, который несёт сам блок; блоки, где скрипт пишет модель, и STscript здесь пропускаются.

### After User

Блок стартует сразу после сохранения сообщения пользователя, и основной ответ, как в оригинальном расширении, ждёт его завершения: результат и то, что блок внедрил, попадают в этот же ответ. Блок с флагом **«Фоновый»** ответ не задерживает. Остановка генерации, пока идут такие блоки, отменяет и сам ответ.

Результат сохраняется у пользовательского сообщения, но отдельная панель под такими сообщениями намеренно не показывается. Инжекция «в последние ответы» ищет результаты у сообщений ассистента, поэтому до `After User` дотягивается только инжекция отдельным блоком промпта (см. «Prompt injection»).

### After Assistant

Это основной режим. Блок запускается после получения ответа ассистента и привязывается к его текущему свайпу.

При включённой Studio запуск происходит после выбора итоговой версии текста, чтобы инфоблок или изображение относились именно к тому ответу, который видит пользователь.

### Periodic

`Periodic` — активный таймерный trigger только для `Script`. Scheduler работает для включённых periodic-блоков активного ExtBlocks-пресета, пока приложение находится на переднем плане и открыт активный визуальный чат.

Интервал хранится в `periodicIntervalSeconds`. Значение по умолчанию — 60 секунд; нулевое или отрицательное значение runtime также трактует как 60 секунд. В текущем редакторе этот интервал изменить нельзя.

При уходе приложения в `inactive`, `paused`, `hidden` или `detached` таймеры отменяются. После возврата в `resumed` они создаются заново и ждут полный интервал: пропущенные срабатывания не догоняются. Если активный чат или сессия сменились, уже начатый tick теряет полномочия и отменяется.

Periodic-запуск не создаёт `InfoBlock` и не сохраняет возвращённое значение. Это side-effect-only сценарий для разрешённых действий вроде изменения переменных, запуска генерации, воспроизведения звука или уведомления.

### Только вручную

Блок с флагом **«Только вручную»** исключается из автоматической цепочки. Его можно запускать индивидуально из панели.

Команда общего запуска использует автоматический процессор `After Assistant`, поэтому такие блоки в общий Run All также не входят.

## Контекст блока

История всегда считается относительно **anchor message** — сообщения, на котором висит блок, а не относительно конца чата.

Настройка количества сообщений работает так:

- `0` — не передавать историю;
- `-1` — передать всю историю до anchor включительно;
- положительное число — передать указанное количество последних сообщений до anchor.

Блок может дополнительно получить:

- несколько прошлых результатов блока с тем же именем;
- `previousOutput` от непосредственного предыдущего блока цепочки;
- данные персонажа и активной персоны.

Карточка (имя, описание, личность, сценарий, примеры диалога) и персона всегда собираются из моделей `Character` / `Persona` и управляются только переключателями «Карточка персонажа» и «Персона пользователя». Из снимка основного промпта они не вырезаются: пресеты часто выключают стандартные блоки и вставляют карточку макросом в свой блок, а фильтр по id блока такой вставки не видит. Стандартные блоки `char_card`, `char_personality`, `scenario`, `example_dialogue` и `user_persona` из снимка убираются, чтобы карточка не пришла дважды. Пользовательский блок пресета с `{{description}}` внутри по-прежнему относится к «Инструкциям основного пресета» — если включить их вместе с карточкой, описание придёт два раза.

## Запрос к провайдеру

Блок идёт к модели тем же путём, что и раньше: `InfoBlockService.generateSingleBlockContent` собирает сообщения и вызывает тот же транспортный слой, что и генерация в чате — `pickChatTransport(apiConfig.protocol)` и `ChatTransportRequest.fromApiConfig`. Поэтому блок получает ровно те же протоколы (OpenAI, Custom Chat Completion, OpenAI Responses, Anthropic, Gemini, OpenRouter), post-processing промпта, sampling-параметры, reasoning-настройки, prompt cache и extra request parameters, что и обычный ответ персонажа. Отдельного «упрощённого» HTTP-клиента у ExtBlocks нет.

Отличия от чата, о которых стоит помнить:

- `stream` в запросе определяется настройкой блока **Stream to panel**, а не флагом `stream` выбранного API-подключения;
- у блока нет сторожевого таймера первого чанка (`IdleTimeoutGuard`), который есть у чата, — зависший ответ снимается только кнопкой Stop;
- `session_id` для sticky-роутинга и прогретого prompt cache в запросе блока не передаётся.

### Профили генерации (`api_preset`)

В оригинале у каждого блока есть `api_preset`: `big`, `medium` или `small`, и у каждого из трёх свои подключение и параметры. В Glaze подключение у пресета ExtBlocks одно, поэтому профиль несёт только параметры. Их задают в разделе API пресета, в группе **«Профили генерации»**:

- температура, top_p, максимум токенов и уровень рассуждений. Пустое поле — значение из подключения, а заданное значение отправляется, даже если в подключении этот параметр выключен;
- **«Запрос подтверждения»** — `confirmation_jb` оригинала: к запросу добавляются ход ассистента `[Please confirm your request]` и ход пользователя `[I confirm]`.

Профиль, в котором ничего не задано, ничего и не меняет, поэтому у пресетов, сохранённых раньше, поведение прежнее. Блок выбирает профиль в редакторе (**«Профиль генерации»**), импорт сохраняет `api_preset` из оригинала. Параметры профиля применяются и к rewrite-блокам, и к `glaze.generateText({ preset })` (по умолчанию — `medium`).

### Один запрос на группу блоков

Как в оригинале (`groupBlocksByContext`), generated-блоки со списком контекста, у которых совпадают имена элементов контекста и флаг `background`, идут к модели **одним запросом**. Каждый блок затем берёт из ответа свой тег; блок, чьего тега в ответе нет, завершается ошибкой. В панели у каждого блока по-прежнему своя строка со статусом, регексы и картинки применяются к каждому отдельно.

- Запрос строится как `getBlocksFullPrompt` оригинала: `Block(s) prompt:` — промпты всех блоков группы, затем `Block(s) template:` — их шаблоны. Это ставится в начало первого системного сообщения контекста, а если контекст начинается не с системного — отдельным системным сообщением перед ним. Так же теперь спрашивается и одиночный блок со списком контекста.
- Контекст общего запроса собирается по первому блоку группы.
- Не группируются: блоки без списка контекста (их запрос собирается по политике контекста Glaze), блоки с «Ждать предыдущий», блоки с готовым содержимым, а также блоки на разных подключениях или профилях генерации — оригинал отправил бы их на подключение первого блока.
- Общий ответ не стримится в панель.

## Макросы

В инструкциях и шаблонах доступны макросы:

- `{{char}}` — имя персонажа;
- `{{user}}` — имя активной персоны;
- `{{description}}` — описание персонажа;
- `{{personality}}` — его характер;
- `{{scenario}}` — сценарий карточки.

Если данных нет, макрос заменяется пустой строкой.

### Макросы оригинального расширения

- `{{ExtBlocks::имя}}` и его синоним `{{ExtBlocks-GetBlockByName::имя}}` — последнее готовое состояние блока с этим именем, вместе с тегами (`<имя>…</имя>`), как в оригинале. Работает и в основном промпте (пресет, карточка, лорбуки — везде, где работает общий движок макросов), и в промптах, шаблонах и контексте самих блоков. Состояние ищется от последнего сообщения назад по показанным свайпам. Есть у generated- и accumulation-блоков; у неизвестного или ещё пустого блока макрос даёт пустую строку.
- `{{mainPrompt}}` — main prompt текущего пресета чата, как он записан.
- `{{wiBefore}}`, `{{wiAfter}}`, `{{wiAll}}` — записи лорбуков, которые активирует **сам запрос блока** (оригинал сканирует промпт блока, а не чат), по их позиции. `{{wiExamples}}` и `{{wiDepth}}` всегда пусты: в лорбуках Glaze нет позиций «примеры» и «по глубине».

`{{mainPrompt}}` и `{{wi*}}` подставляются в уже собранный запрос блока, как `checkAllMacros` оригинала. Лорбуки и пресет читаются, только если запрос эти макросы содержит.

В пути prompt injection надёжно доступна активная персона, но объект персонажа сейчас не передаётся полностью. Поэтому часть character-макросов при повторной инъекции может раскрыться не так, как при первоначальном запуске блока.

### Отдельный урезанный движок макросов

ExtBlocks раскрывают макросы своим маленьким расширителем
(`lib/features/extensions/services/macro_expander.dart`), а не общим движком
`lib/core/llm/macro_engine.dart`, который обслуживает промпт, чат и регексы.
Отсюда расхождения, о которых стоит помнить:

- поддерживаются только пять макросов из списка выше и макросы оригинала (см. выше). `{{persona}}`,
  `{{mesExamples}}`, `{{time}}`, `{{date}}`, `{{roll::}}`, `{{random::}}`,
  `{{getvar::…}}`, `{{getglobalvar::…}}`, `{{gametime}}` и остальные остаются в
  тексте блока литералами;
- однобрейсные формы (`{char}`, `{user}`), которые понимает основной движок,
  не распознаются;
- совпадение идёт по точной строке: `{{ user }}` с пробелами не заменится;
- `{{user}}` без активной персоны даёт **пустую строку**, тогда как чат и
  промпт в этом случае подставляют `User`.

Где раскрытие происходит, а где нет:

| Путь | Раскрывается |
|------|--------------|
| Панель результатов ExtBlocks (`block_panel_updater`, `chat_webview_panel_refresher`) | да, при каждом рендере из сырого содержимого |
| Инъекция блока в историю (`info_block_injector`) | да |
| Инструкции блока и `contextSystemPrompt` (`info_block_service`) | да |
| `template` блока | нет — подставляется только `{{name}}`, модель видит `{{user}}` буквально и часто копирует его в ответ |
| HTML панели, уходящий в `openPanel` (`generated_block_handler`) | да — раскрывается перед передачей в iframe |

В базе содержимое блока хранится сырым (с макросами) намеренно: подстановка
идёт на рендере, чтобы смена персоны меняла и старые блоки. HTML панели
раскрывается один раз, в момент передачи в iframe, — панель живёт в отдельном
документе и через панель результатов не перерисовывается.

### Регексы

Поведение повторяет оригинальное расширение, где результат блока попадает в
`display_text` сообщения и рендерится тем же проходом регексов, что и обычный
ответ.

- **Панель результатов** проходит **display-проход** регексов
  (`isMarkdown: true`, placement AI_OUTPUT) при каждом рендере, из сырого
  содержимого — через `applyExtBlockDisplayRegexes` в `block_panel_updater` и
  `chat_webview_panel_refresher`. Поэтому скрипт с флагом «Only Format Display»
  (`markdownOnly`), который превращает теги модели в HTML-карточку, срабатывает
  у блока так же, как у сообщения.
- **Поле блока «Применять замены текста»** (`applyRegex`) прогоняет уже
  извлечённое содержимое через **prompt-проход** регексов (`isPrompt: true`,
  depth 0) в момент генерации и сохраняет результат — как `apply_regex` в
  апстриме. По умолчанию выключено.
- **HTML интерактивной панели** (`render: panel`) регексами **не**
  обрабатывается: его получает sandboxed-iframe, а не display-проход.
- Проход берёт тот же набор скриптов, что и рендер чата: активный пресет (кроме
  режима Studio) плюс глобальные регексы.

### Context Builder

Если у блока есть **непустой список `context`**, рантайм собирает запрос из него
и не трогает `contextPolicy` / `contextMessageCount` / снимок основного
контекста — ровно как в оригинале, где список и есть весь контекст. Сборка
живёт в `blocks/context_item_builder.dart`, вызов — из `InfoBlockService`.

- Поддерживаются все пять типов: `text` (раскрывается тем же урезанным
  расширителем, что и промпт блока — см. выше), `last_messages`,
  `last_messages_keyword`, `last_messages_by_block`, `previous_block`.
- Учитываются `messages_count` (положительный — с конца, отрицательный — с начала),
  `messages_offset`, `keyword_stopper`, `block_count`, роль элемента,
  `disabled`, разделитель и префиксы/суффиксы пользователя и персонажа.
- Потянутые из чата сообщения проходят **prompt-проход** регексов с их глубиной
  (placement 1 для пользователя, 2 для персонажа), как `getRegexedString` в
  оригинале.
- Элементы с одинаковой ролью склеиваются в одно сообщение; инструкция блока
  (prompt + template) остаётся ведущим system-сообщением.
- `previous_block` читает сохранённые результаты блоков по имени и оборачивает их
  обратно в тег; пустое `block_name` (как в импортах, где элемент не настроен)
  даёт пустую строку.
- Если список не дал ни одного сообщения, сборка откатывается на обычный путь,
  чтобы блок не уехал пустым запросом.

**Редактор** (`screens/preset_editor/sections/context_list_section.dart`) —
группа «Список контекста» в редакторе generated- и rewrite-блоков, как Context
Builder оригинала: добавить, изменить, выключить, перетащить, удалить пункт.
У пункта обязательно название; поля зависят от типа. В префиксах и суффиксах
`\n` — перенос строки, как в оригинале. Импорт и экспорт идут файлом
`context.json` формата оригинала (`{"items": [...]}`). Импорт заменяет список,
пунктам без `id` выдаётся новый. Пока в списке есть включённый пункт, старые
настройки контекста (число сообщений, текст перед историей, прошлые выводы,
политика) скрыты, потому что не используются.

Редактора этого списка в UI пока нет: он сохраняется, уходит обратно при экспорте
и используется рантаймом, но правится только правкой JSON блока.

## Порядок и зависимости

Перед запуском блоки сортируются по полю `order`.

Независимые блоки могут выполняться параллельно. Это сокращает общее время, если, например, инфоблок и изображение не используют результаты друг друга.

Флаг **«Ждать завершения предыдущего блока»** создаёт простую цепочку:

```text
Блок A
   |
   | previousOutput
   v
Блок B
```

Зависимый блок ждёт только непосредственного соседа перед ним. Это не полноценный граф зависимостей: нельзя выбрать произвольный block ID или построить сложную топологию.

Если предыдущий блок завершился ошибкой, его сохранённый HTML с сообщением об ошибке всё равно может попасть в `previousOutput` следующего блока.

## ExtBlocks и Studio

### Studio выключена

После основного ответа ExtBlocks запускаются в фоне. Чат не обязан удерживать кнопку Stop до окончания всех дополнительных блоков.

Результаты привязываются к верхнему свайпу ответа без отдельного Studio sub-swipe.

### Studio включена

Сначала Studio определяет итоговый текст:

- очищенную версию;
- исходную версию, если Cleaner ничего не изменил;
- fallback или частичный результат при соответствующем сценарии.

Только после этого ExtBlocks привязываются к выбранной паре `swipeId` и `agentSwipeId`. Благодаря этому изображение или панель не остаются прикреплёнными к черновой версии, когда пользователь видит очищенную.

В некоторых аварийных ветках Cleaner ExtBlocks могут не запуститься. Поэтому включённая Studio не является абсолютной гарантией запуска каждого блока.

## Свайпы и результаты

Каждый обычный результат ExtBlocks хранит:

- сессию;
- сообщение;
- верхний свайп;
- внутренний Studio-свайп;
- идентификатор, имя и тип блока;
- содержимое;
- порядок и статус;
- время создания.

При переключении ответа панель ищет результаты именно для текущей пары свайпов. Для старых данных поддерживается fallback к legacy-варианту без внутреннего Studio-свайпа.

Ручной запуск блока из панели использует ту же привязку, под которой уже лежат результаты этого сообщения. Для блока с сохранённым результатом это его собственная пара свайпов, для блока в состоянии «ожидает» — привязка его соседей. Иначе новая запись попала бы в другую пару, точное совпадение перестало бы быть пустым, и уже готовые соседние блоки снова показались бы как «ожидает».

## Prompt injection

По умолчанию у блока установлено:

```text
inject = false
```

Это означает, что результат:

- сохраняется;
- показывается пользователю;
- не влияет на будущую прозу.

Такой режим особенно безопасен при использовании Studio Canon: пользовательские панели не смешиваются с канонической памятью.

Если включить **«Инжектировать в промпт»**, есть два способа (`injectTarget`):

- **В последние ответы** (`history`, по умолчанию для блоков, созданных в Glaze). Результат добавляется к одному или нескольким последним сообщениям ассистента. Каждый блок прикрепляется к тому сообщению, для которого был создан. Между ответом и блоком можно добавить пользовательский префикс.
- **Отдельным блоком промпта** (`prompt`, как в оригинальном расширении; так приходят все импортированные блоки). В запрос попадает один блок — последний готовый результат этого блока в чате, найденный от конца чата назад по любым сообщениям. Он оформлен тегами шаблона и размещается по роли (`injection_role`), позиции (`injection_position`) и глубине (`injection_depth`): сразу после основного промпта, сразу перед ним или в чате на заданной глубине. Отрицательная глубина считается как в оригинале (`сообщений − глубина`), то есть ставит блок выше всего чата. Если у пресета нет блока `main`, блоки «до/после основного промпта» встают в самое начало. Такие блоки собираются при каждой сборке промпта и едут вместе с runtime-инъекциями JavaScript.

Интерфейс отдельно предупреждает, что инжекция не рекомендуется вместе со Studio Canon.

### Флаги состояния

- **Скрыть из панели** (`hide_display`) — блок работает и инжектируется как обычно, но его строки и заглушки в панели не показываются.
- **Фоновый** (`background`) — цепочка не ждёт блок: запуск считается завершённым, пока он ещё работает, а результат появляется в панели, когда готов. Кнопка «Стоп» его по-прежнему останавливает. Блок, зависящий от предыдущего, всё равно ждёт фоновый.

Заглушка «ожидает» в панели не показывается для блоков с ключевым словом или периодом больше 2: их отсутствие под большинством ответов ожидаемо.

### Runtime injection из JavaScript

`glaze.injectPrompt` — другой механизм. Он не связан с полем `inject` у блока.

JavaScript может временно создать prompt-block с:

- идентификатором;
- содержимым;
- ролью `system`, `user` или `assistant`;
- глубиной размещения.

Такие блоки хранятся только в памяти приложения и исчезают после перезапуска. Размер и идентификаторы ограничены, а само действие требует разрешения пресета.

## JavaScript и безопасность

Текущие `Script` и `Periodic` выполняются через `ChatBridgeController` активного визуального чата. Скрипт запускается внутри отдельного невидимого iframe с `sandbox="allow-scripts"`, без `allow-same-origin`; `JsEngineService` в этом runtime-пути не используется. Если активного chat bridge нет, запуск пропускается или завершается ошибкой в зависимости от сценария.

Визуальный bridge ограничивает выполнение тайм-аутом примерно 55–60 секунд.

### Разрешения пресета

По умолчанию потенциально чувствительные возможности запрещены. Пресет отдельно разрешает:

- чтение и изменение переменных чата, персонажа, сообщения или глобальных данных;
- дополнительную генерацию текста;
- запуск основной генерации;
- временную инъекцию в промпт;
- выполнение команд;
- воспроизведение аудио;
- показ уведомлений.

Если проверка разрешения отсутствует, применяется правило **default deny**.

### Честная модель безопасности

Sandbox защищает от прямого доступа к родительскому WebView и API-ключам. Но разрешённые методы `glaze.*` специально создают мост наружу.

HTML сообщений и ExtBlocks перед вставкой проходит `assets/chat_webview/bridge/html_sanitizer.js`. Для сообщений вырезается только код (`<script>`, `<iframe>`/`<object>`/`<embed>`, `on…=`, `srcdoc`, `javascript:`/`data:`-документы), а разметка и CSS попадают в shadow root без изменений — тумблер JS не меняет рендер. Для ExtBlocks действует строгая политика элементов и атрибутов, а их CSS ограничивается областью `.ext-block-content`. Интерактивная панель намеренно является исключением: её HTML остаётся исполняемым, но загружается только внутрь отдельного sandboxed iframe.

Поэтому интерактивные панели и `Script` нельзя считать безопасной средой для произвольного недоверенного кода. Безопасность зависит от null-origin sandbox, выданных разрешений, проверок источника сообщений и доверия к автору пресета.

## Ошибки и остановка

Блок может находиться в одном из состояний:

- ожидает;
- выполняется;
- готов;
- завершён с ошибкой;
- остановлен.

Статус «ожидает» получают только блоки, которые действительно могут выполниться под этим сообщением: `After Assistant` и такого типа, который runtime умеет выполнять. Блоки `After User`, `Periodic`, `Rewrite` (он меняет само сообщение) и `Accumulation` (у него результат есть, только если пришло обновление) не показываются в панели ответа, пока у них нет сохранённого результата, — заполнить их здесь всё равно нечем.

Ошибка сохраняется как отдельное оформленное содержимое блока, поэтому пользователь видит её прямо в панели. Текст ошибки проходит через общий `formatError()` — тот же помощник, которым чат оформляет неудачную генерацию, — поэтому в панели видно «HTTP 401 - Unauthorized» и сообщение провайдера, а не Dio-дамп.

Автоматического цикла повторных попыток на уровне общей оркестрации нет. Повтор запускает пользователь:

- **«Перегенерировать»** — заново выполнить один блок;
- **«Картинка»** — перерисовать только картинки блока;
- **«Запустить блоки»** — повторить набор `After Assistant`. Кнопка появляется, только когда в этом наборе есть незавершённый блок, и удаляет результаты лишь тех блоков, которые сама же перезапускает.

Кнопка Stop выглядит относящейся к одному блоку, но сейчас отменяет все активные ExtBlocks-задачи через общий набор cancel tokens.

После перезапуска приложения оставшиеся записи со статусом `running` переводятся в `stopped`.

## Хранение и синхронизация

Пресеты и результаты ExtBlocks хранятся в локальной базе данных. Настройка включения и идентификатор активного пресета сохраняются отдельно.

Presets и InfoBlocks входят в архитектуру резервного копирования и облачной синхронизации.

Сгенерированные изображения сохраняются отдельными PNG-файлами, а в результате блока остаётся ссылка на локальный путь.

## Важные ограничения

- `Periodic` работает только для `Script`, только с активным foreground-чатом и без catch-up после паузы; интервал пока нельзя изменить в UI.
- Результаты `After User` не показываются под пользовательским сообщением и не инжектируются в последние ответы — только отдельным блоком промпта.
- Run All выполняет цепочку `After Assistant`, а не все существующие trigger-типы, и не проверяет ключевое слово и период.
- STscript не исполняется: script-блок со `script_type: stscript` завершается ошибкой.
- Второй проход accumulation не ждёт фоновые (`background`) generated-блоки: обновитель в их выводе применится только при повторном запуске блоков сообщения.
- Пауза генерации (`generation_pause`) пока не выполняется.
- Блоки **«Только вручную»** не входят в Run All: их запускают по кнопке «Запустить» у самого блока.
- Переключатель стриминга у блока с `render: panel` пока не подключён к LLM callback.
- Context Builder оригинального расширения (упорядоченный список context-items с типами `text` / `last_messages` / `last_messages_keyword` / `last_messages_by_block` / `previous_block` и их префиксами, суффиксами, разделителями и смещениями) рантайм собирает как в апстриме; редактор списка есть в редакторе блока (см. «Context Builder»).
- Обычный HTML сообщений и ExtBlocks санитизируется; HTML панели остаётся исполняемым внутри sandboxed iframe.
- Ошибка предыдущего блока может стать входом следующего зависимого блока.
- Интерактивный iframe не гарантированно восстанавливается после перезагрузки WebView.
- Расширитель макросов ExtBlocks знает только пять общих макросов и макросы оригинала — см. «Отдельный урезанный движок макросов».
- Остановка одного блока сейчас может остановить остальные активные блоки.
- Prompt injection не учитывает внутренний Studio-свайп столь же строго, как панель результатов, поэтому при сложной истории sub-swipes возможны неоднозначности.

## Глоссарий

| Термин | Определение |
|---|---|
| **ExtBlocks / External Blocks / Внешние Блоки** | Система дополнительных задач и панелей вокруг основной генерации чата. |
| **ExtensionPreset** | Набор блоков, API-профилей и JavaScript-разрешений. |
| **BlockConfig** | Настройки одного блока: тип, trigger, порядок, контекст, `render` и поведение. |
| **Generated** | Блок, берущий содержимое у модели или из собственного поля. |
| **Script** | Генерация или выполнение JavaScript в sandbox. |
| **render** | Куда попадает готовое содержимое: `card` или `panel`. |
| **source** | Откуда берётся содержимое: `model` или `carried`. |
| **staticContent** | Содержимое, заданное на самом блоке вместо обращения к модели. |
| **Image Gen** | Провайдер, превращающий текстовое описание в изображение. |
| **Interactive Panel** | Режим `render: panel` — HTML-интерфейс в отдельном sandboxed iframe. |
| **Trigger** | Событие, запускающее блок. |
| **After User** | Запуск после сохранения сообщения пользователя, параллельно ответу. |
| **After Assistant** | Запуск после финализации ответа ассистента. |
| **Periodic** | Side-effect-only запуск Script по таймеру в активном foreground-чате; без catch-up после паузы. |
| **Manual only** | Режим, исключающий блок из автоматической цепочки. |
| **Anchor message** | Сообщение, относительно которого собирается история блока. |
| **previousOutput** | Содержимое непосредственного предыдущего блока цепочки. |
| **previousBlocksCount** | Количество старых результатов блока с тем же именем. |
| **Dependency** | Ожидание предыдущего блока и передача его результата следующему. |
| **Prompt injection** | Добавление сохранённого результата ExtBlocks к истории ассистента. |
| **Runtime prompt injection** | Временный prompt-block, созданный через `glaze.injectPrompt`. |
| **Capability** | Явное разрешение пресета на действие JavaScript. |
| **Default deny** | Запрет действия, если разрешение не было явно выдано. |
| **Headless engine** | Невидимый WebView, реализованный `JsEngineService`, но не используемый текущими Script и Periodic runtime-путями. |
| **Visual chat bridge** | Активный `ChatBridgeController`, через который Script и Periodic запускают sandboxed iframe. |
| **Sandbox** | Ограниченная среда исполнения HTML или JavaScript. |
| **swipeId** | Идентификатор выбранного верхнего варианта ответа. |
| **agentSwipeId** | Идентификатор внутреннего варианта Studio, например очищенного текста. |
| **Cleaner** | Редакторская фаза Studio, после которой выбирается итоговый текст. |
| **InfoBlock row** | Сохранённый в базе результат одного запуска блока. |
| **Rerun** | Ручной повтор выполнения блока. |
